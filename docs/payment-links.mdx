# Liens de paiement

Les liens de paiement sont rattachés à une application PichFlow. Leur adresse publique est construite à partir de `APP_URL`, par exemple `http://localhost:3000/pay/<slug>` en local ou `https://votre-domaine/pay/<slug>` en production.

## Routes

| Méthode | Route | Accès |
|---|---|---|
| `GET` | `/api/payment-links?applicationId=<id>` | Session authentifiée, application sélectionnée |
| `POST` | `/api/payment-links` | Session authentifiée, application propriétaire |
| `GET` | `/api/payment-links/slug/:slug` | Public, uniquement si le lien est actif, non expiré et sous son plafond |
| `GET`, `PUT`, `DELETE` | `/api/payment-links/:id` | Session authentifiée, application sélectionnée |

Ces routes utilisent la session du tableau de bord, pas une clé d'API marchande `/api/v1`.

## Création

Exemple de corps de requête authentifiée :

```json
{
  "applicationId": "app_...",
  "title": "Licence professionnelle",
  "description": "Accès aux modules",
  "isFixedAmount": true,
  "amount": 15000,
  "currency": "XOF",
  "country": "BJ",
  "requirePhone": false,
  "expiresAt": "2027-10-19",
  "usageLimit": 20
}
```

- Un montant fixe doit être un entier d'au moins 200 XOF. La devise est actuellement limitée à XOF.
- Pour un montant libre, envoyez `"isFixedAmount": false` sans `amount`. Le client choisit son montant sur la page publique; le serveur le revalide avant la création de facture.
- `country` est facultatif. La configuration vérifiée dans ce dépôt ne propose actuellement que le Bénin (`BJ`); le client doit le choisir si aucun pays par défaut n'est défini.
- `requirePhone` est facultatif et vaut `false` par défaut. Quand il est activé, le numéro de contact est validé avant de continuer. Il reste distinct du numéro nécessaire au moyen de paiement.
- `expiresAt` est une date ISO `YYYY-MM-DD` facultative; le lien cesse d'être utilisable après la fin de cette journée UTC.
- Le serveur génère le slug public aléatoire et renvoie `paymentUrl`.

## Parcours public et moyens de paiement

Le client n'a pas besoin de compte PichFlow. Le checkout collecte les coordonnées nécessaires, demande le pays configuré, puis crée une facture et redirige vers le checkout hébergé. La sélection de carte ou d'un portefeuille mobile est laissée à la page sécurisée du fournisseur : PichFlow n'accepte ni numéro de carte ni cryptogramme, et n'envoie pas de `channels` au fournisseur. La page hébergée n'affiche que les moyens activés dans la configuration du compte marchand.

Le dépôt ne valide pas individuellement les moyens listés dans la documentation PayDunya ni leur activation sur le compte sandbox. Ils ne sont donc pas présentés comme disponibles dans PichFlow. La configuration locale actuelle limite le pays au Bénin et la devise à XOF.

## URLs et callbacks

Définissez `APP_URL` sur l'origine publique du site en production. En local, les URL de retour du navigateur peuvent pointer vers localhost; un callback serveur localhost n'est pas joignable depuis PayDunya. Pour tester l'IPN en local, définissez `PAYDUNYA_CALLBACK_URL` sur l'URL HTTPS publique d'un tunnel vers `/api/webhooks/paydunya`. La variable n'est pas requise pour la vérification serveur déclenchée au retour du navigateur.

La création de facture ne confirme pas le paiement. PichFlow vérifie ensuite le token côté serveur; l'IPN est décodée à partir du champ documenté `data`, et son hash SHA-512 est comparé au hash de la Master Key avant la vérification du statut. Seul le statut confirmé met à jour la transaction.

## Frais

PichFlow ne majore pas le montant et ne déduit pas de frais supposés. Le flux standard documenté ne fournit pas de montant de frais vérifié dans la réponse utilisée ici; les frais et le montant net restent donc non confirmés plutôt que présentés comme des montants reçus.
