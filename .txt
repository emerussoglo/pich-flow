# PICHFLOW — MISSION CIBLÉE : FINALISER ET FIABILISER LES LIENS DE PAIEMENT PAYDUNYA

Tu travailles directement dans le dépôt local de mon projet PichFlow. Tu as accès au code source. Ta mission est de **faire fonctionner le paiement de bout en bout, en local et en ligne**, en conservant l'intégration PayDunya existante lorsqu'elle fonctionne déjà.

Ne refais pas tout le dashboard. Ne modifie pas les fonctionnalités sans rapport avec le paiement. Inspecte d'abord le code existant, identifie les causes des problèmes et effectue les corrections nécessaires.

Documentation officielle :
https://developers.paydunya.com/doc/FR/introduction
https://developers.paydunya.com/doc/FR/http_json

## 1. Commencer par comprendre le paiement existant

J'ai déjà réalisé un paiement de test de 15 000 XOF pour « Licence Pro PitchFlow ». PayDunya a enregistré la facture, le client fictif, la référence PichFlow et les URL de redirection. Mon application affiche également un message de paiement confirmé.

Ne casse pas cette partie qui semble déjà fonctionner.

Inspecte précisément :

- La route qui crée un lien de paiement.
- La page publique qui reçoit le client.
- La route backend qui crée la facture PayDunya.
- Le service ou module qui utilise les clés PayDunya.
- Le callback `/api/webhooks/paydunya`.
- La route ou la page de retour qui vérifie le paiement.
- La manière dont le statut, la référence, le montant, la devise et l'application sont enregistrés en base.
- Les erreurs actuellement visibles dans le terminal et dans le navigateur.

Reproduis les problèmes avant de les corriger. Ne remplace pas une intégration qui fonctionne partiellement par une intégration entièrement nouvelle sans raison technique démontrée.

## 2. Corriger la création du lien de paiement

Dans la page « Liens de paiement », supprime complètement l'aperçu simulé ordinateur/téléphone et les options de prévisualisation ajoutées précédemment.

Le formulaire de création doit contenir :

- Nom du produit ou du service, obligatoire.
- Description, facultative.
- Choix du type de montant : **montant fixe** ou **montant libre**.
- Si le montant est fixe : afficher le champ montant et le sélecteur de devise.
- Si le montant est libre : ne pas demander de montant à la création ; le client le saisira sur la page publique.
- Pays par défaut, facultatif.
- Date d'expiration, facultative.
- Case facultative : demander le numéro de téléphone du client dès la première étape du checkout.

Lorsque le type de montant change, adapte les champs affichés et les validations. Un lien à montant libre ne doit pas être enregistré avec un montant fixe fictif. Un lien à montant fixe doit refuser un montant nul, négatif ou invalide.

La devise proposée doit être cohérente avec les devises prises en charge par le produit et les moyens de paiement configurés. Ne déduis pas automatiquement qu'une devise est disponible simplement parce qu'un pays est sélectionnable.

À la création :

1. Enregistre correctement le lien.
2. Génère un identifiant public unique.
3. Affiche l'URL finale, avec un bouton pour la copier.
4. Permets de retrouver et d'ouvrir le lien.
5. Vérifie l'expiration côté serveur.
6. Empêche toute modification du montant ou de la devise par le client lorsque le lien est à montant fixe.

## 3. URLs publiques : local et production

Les liens doivent utiliser une structure claire, par exemple :

- Local : `http://localhost:3000/pay/IDENTIFIANT_PUBLIC`
- Production : `https://pichflow.vercel.app/pay/IDENTIFIANT_PUBLIC`

Adapte ces exemples à la structure de routes réellement présente dans le projet. Le format définitif doit être uniforme, stable et sans doubles barres inutiles.

Centralise la construction de l'URL dans une configuration serveur fondée sur une variable d'environnement appropriée, telle que `APP_URL` ou le nom de variable déjà utilisé dans le projet.

N'inscris jamais `localhost` en dur dans les URL utilisées en production.

Pour chaque transaction, génère les URL `return_url`, `cancel_url` et `callback_url` selon l'environnement réel. En local, utilise les URL locales pour les retours navigateur. Pour le callback serveur, utilise une URL réellement joignable par PayDunya, par exemple un tunnel HTTPS temporaire pendant les tests locaux si nécessaire. En production, utilise l'URL HTTPS publique du site déployé.

Ne considère pas un callback vers `localhost` comme fonctionnel pour un paiement initié depuis Internet.

## 4. Construire le checkout public en trois étapes

Le client ne doit pas avoir à se connecter à PichFlow. Il ouvre le lien et suit les étapes ci-dessous.

### Étape 1 — Informations personnelles

Afficher :

- Prénom.
- Nom.
- Adresse e-mail.
- Numéro de téléphone de contact si la collecte est activée pour ce lien.

Le numéro de contact est facultatif lorsque le créateur n'a pas activé cette option. Il ne faut pas le confondre avec le numéro qui sera utilisé ensuite pour le paiement Mobile Money.

Le nom, le prénom et l'e-mail sont validés avant de poursuivre. Si le numéro de contact est obligatoire pour ce lien, bloque la progression tant qu'il n'est pas valide.

Conserve les informations de l'étape 1 pendant le parcours, sans les exposer dans l'URL ni les enregistrer inutilement dans le navigateur.

### Étape 2 — Choix du pays et du moyen de paiement

Afficher un sélecteur de pays avec :

- Drapeau.
- Nom du pays.
- Barre de recherche.
- Liste déroulante accessible sur mobile et ordinateur.

Utilise uniquement les pays et méthodes de paiement réellement disponibles dans la configuration PayDunya que nous utilisons.

Les pays et moyens à configurer ou vérifier en priorité sont :

**Sénégal**
- Carte bancaire, lorsque prise en charge.
- Orange Money Sénégal.
- Expresso SN.
- Free Money Sénégal.
- Wave Sénégal.
- Djamo SN.

**Bénin**
- Carte bancaire, lorsque prise en charge.
- Moov Bénin.
- Celtiis Cash.

**Burkina Faso**
- Carte bancaire, lorsque prise en charge.
- Orange Money Burkina.
- Moov Burkina Faso.

**Côte d'Ivoire**
- Carte bancaire, lorsque prise en charge.
- Orange Money CI.
- MTN CI.
- Moov CI.
- Wave CI.
- Djamo CI.

**Mali**
- Carte bancaire, lorsque prise en charge.
- Orange Money Mali.

**Togo**
- Carte bancaire, lorsque prise en charge.
- TMoney Togo.
- Moov Togo.

**Cameroun**
- Carte bancaire, lorsque prise en charge.
- MTN Cameroun.

Les noms ci-dessus sont les libellés d'interface souhaités. Vérifie les identifiants techniques exacts attendus par PayDunya dans la documentation officielle. Ne transmets pas directement les libellés français à l'API si PayDunya attend des codes différents.

Vérifie également si certains moyens nécessitent une configuration ou une activation sur le compte PayDunya. N'affiche pas comme disponible un moyen qui n'est pas utilisable dans notre configuration de test.

Quand le pays est sélectionné, filtre les moyens compatibles. Quand le pays change, efface un moyen précédemment sélectionné s'il n'est plus compatible.

Après le choix du moyen, affiche le champ correspondant aux informations nécessaires. Pour Mobile Money, il peut s'agir du numéro de paiement. Ce numéro est distinct du numéro de contact de l'étape 1.

Pour la carte bancaire, utilise le parcours sécurisé pris en charge par PayDunya. Ne collecte pas le numéro complet de carte ni son cryptogramme dans les formulaires PichFlow si le flux officiel de redirection est utilisé.

Si PayDunya impose que le client sélectionne son moyen de paiement directement sur sa page hébergée, conserve cette redirection sécurisée plutôt que de simuler une intégration directe.

### Étape 3 — Récapitulatif et bouton Payer

Afficher le produit, la description, le montant, la devise, le pays, le moyen sélectionné et les informations du client nécessaires à la confirmation.

Pour un lien à montant fixe, afficher le montant du lien et interdire sa modification.

Pour un lien à montant libre, demander le montant au client, valider la valeur côté serveur et empêcher tout montant nul, négatif ou invalide.

Le bouton **Payer** doit déclencher une vraie transaction. Il ne doit pas simplement afficher une animation ou un message de succès simulé.

## 5. Intégration PayDunya : préserver ce qui marche et corriger le reste

Inspecte les noms et les usages des variables d'environnement PayDunya déjà présentes. Ne remplace pas mes clés et ne les affiche jamais.

Vérifie le mode test et l'endpoint correspondant. Pour le paiement par redirection, compare l'implémentation avec le flux officiel de création de facture et de vérification du statut.

Le backend doit :

1. Vérifier le lien et son application propriétaire.
2. Vérifier le montant et la devise.
3. Créer une transaction interne en attente.
4. Construire la facture PayDunya.
5. Envoyer les données requises et les informations client autorisées.
6. Envoyer les URL de retour et de callback correctes.
7. Vérifier `response_code` et les autres champs nécessaires de la réponse.
8. Enregistrer le jeton PayDunya et la référence PichFlow.
9. Rediriger le client vers l'URL de paiement effectivement retournée par PayDunya.
10. Gérer les erreurs et les délais d'attente sans perdre l'état de la transaction.

Ne suppose pas qu'une facture est payée parce qu'elle a été créée avec succès. La création de facture et la confirmation du paiement sont deux étapes différentes.

## 6. Statuts de paiement fiables

Après le paiement, affiche un écran de résultat clair :

- Paiement confirmé.
- Paiement en attente de confirmation.
- Paiement échoué.
- Paiement annulé.

Ne marque la transaction comme payée qu'après confirmation serveur fiable.

Lors du retour du client, récupère le jeton retourné par PayDunya et vérifie le statut depuis le backend. Le callback doit également vérifier les données reçues conformément à la documentation officielle, y compris la validation du hash si elle s'applique au flux utilisé.

Le callback PayDunya reçoit une requête POST au format documenté. Vérifie son traitement réel, notamment le champ `data` lorsque ce format est utilisé.

Protège les mises à jour de statut contre les doublons et les appels concurrents. Une même transaction ne doit pas être comptabilisée plusieurs fois.

Le statut affiché au client, celui enregistré en base et celui visible dans le dashboard doivent rester cohérents.

## 7. Frais de transaction

Je souhaite que les frais applicables au paiement soient pris en compte, et non absorbés arbitrairement par PichFlow.

Cependant, vérifie d'abord ce que PayDunya facture réellement et ce que son API renvoie.

- Si le flux PayDunya utilisé fournit un montant de frais vérifiable et un montant net, enregistre ces valeurs.
- Si les frais ne sont pas exposés par l'API, ne les invente pas.
- Si une surcharge doit être ajoutée au montant payé par le client, elle doit être explicitement définie, autorisée et affichée avant confirmation.
- Ne déduis jamais deux fois les frais.
- Ne présente pas un montant net estimé comme un montant officiel reçu.

Vérifie si PayDunya permet réellement de faire supporter les frais au payeur dans notre configuration. Si cette possibilité n'est pas fournie par le flux standard, indique la limite et propose une solution techniquement compatible sans inventer une fonctionnalité.

## 8. Isolation des applications

Tous les liens et toutes les transactions doivent appartenir à une application PichFlow précise.

Lors de la création d'un lien, vérifie que l'utilisateur authentifié possède l'application sélectionnée.

Lors du checkout public, retrouve le lien par son identifiant public, puis récupère son application propriétaire. Toutes les transactions, les clients, les statuts et les statistiques associés doivent utiliser cette application.

Ne fais pas confiance à un `appId` fourni par le navigateur sans vérification serveur.

Les pages de clients, de transactions et de soldes doivent afficher uniquement les données de l'application sélectionnée. Une transaction d'une application A ne doit jamais apparaître dans B.

Ajoute au minimum un test d'intégration avec deux applications et des liens différents pour vérifier l'absence de fuite de données.

## 9. Interface de paiement

Je veux une interface PichFlow simple, professionnelle et cohérente sur mobile et ordinateur.

- N'affiche pas « PayDunya » comme marque ou fournisseur dans l'interface publique destinée au client.
- Le client doit voir l'identité du marchand, le produit ou service, le montant et les étapes nécessaires au paiement.
- Ne masque pas les informations légalement requises ni les mentions de sécurité nécessaires.
- N'invente pas de méthode de paiement ou de logo d'opérateur.
- Affiche un indicateur de progression pendant la création de facture ou la redirection.
- Désactive temporairement le bouton Payer pendant la soumission pour éviter les doublons.
- Affiche des messages compréhensibles en cas d'erreur.
- Supprime l'aperçu ordinateur/téléphone du formulaire de création de lien.
