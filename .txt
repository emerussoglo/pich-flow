## Comparatif des Solutions

| **Critère**                 | **Checkout Hébergé**                                             | **Softpay Direct**                                                            |

| **Cas d’usage recommandés** | E-commerce standard, abonnements SaaS, factures ponctuelles      | Applications mobiles natives, bornes de commande, tunnels de vente sur-mesure |

## Règles Fondamentales de Gestion des Montants

1. **Formatage décimal chaîne** : Selon la spécification officielle SasPay, tous les montants transmis dans les payloads doivent être des chaînes avec exactement deux décimales (ex: **`"15000.00"`**, **`"250.50"`**). Les flottants JavaScript bruts sont strictement déconseillés afin d’éviter les erreurs d’arrondi.
2. **Gestion des frais (`fee_charge_mode`)** :
   - **`ADD_ON`** : Les frais de passerelle sont ajoutés en supplément au total à payer par le client final.
   - **`DEDUCTED`** : Les frais de passerelle sont absorbés par le marchand et déduits du montant net perçu.

# Liens de paiement

Créez, partagez et gérez des liens de paiement à montant fixe ou libre sans rédiger de code supplémentaire.

# Liens de Paiement

Les **Liens de Paiement** PichFlow permettent de générer une URL publique partageable (par WhatsApp, email, SMS ou sur les réseaux sociaux) permettant à vos clients de régler une prestation ou un produit en toute simplicité.

---

## Types de Liens de Paiement

PichFlow gère deux types de liens :

1. **Montant Fixe (`isFixedAmount: true`)** : Idéal pour un produit, un forfait d’abonnement ou un événement précis (ex: 15 000 XOF).
2. **Montant Libre (`isFixedAmount: false`)** : Idéal pour les dons, cagnottes ou facturations personnalisées où le client saisit le montant qu’il souhaite vous verser.

---

## Gestion depuis le tableau de bord

Les pages existantes décrivent la création et la gestion des liens depuis le tableau de bord. Le serveur confirme des routes de gestion des liens protégées par la session du compte, mais aucune route **`/v1/payment-links`** authentifiée par clé API n’a été trouvée. Aucun exemple de requête publique par clé API n’est donc fourni ici.

### Exemple de champs décrits
```
{
  "title": "Abonnement annuel",
  "amount": 25000,
  "currency": "XOF",
  "isFixedAmount": true,
  "country": "BJ"
}

```

Ces champs sont issus de la documentation existante ; le format de réponse et l’URL publique d’un lien doivent être confirmés dans le tableau de bord avant de les traiter comme un contrat d’API.

---

## Cycle de Vie & Suivi des Liens

- **Consultation des transactions par lien** : Chaque règlement effectué sur un lien incrémente automatiquement son compteur **`paymentCount`** et son volume total encaissé **`totalCollected`**.
- **Désactivation** : Le code confirme une action de mise à jour des liens via l’API du tableau de bord. Aucun chemin public **`/v1/payment-links/:id`** n’a été confirmé.
- **Plafond d’utilisation** : Vous pouvez restreindre le nombre maximum de règlements autorisés (ex: stock limité à 50 exemplaires).

# Vérification des Paiements

Méthodes de réconciliation, polling d’état et arbitrage entre Webhooks et vérification active.

# Vérification des Paiements

La confirmation d’un paiement en Afrique nécessite une synchronisation robuste entre les télécoms, la passerelle SasPay et votre serveur.Pour garantir une expérience sans faille, PichFlow préconise une **approche hybride** combinant les webhooks asynchrones et la vérification active (polling sécurisé).

---

## 1. Webhook (Mécanisme Principal Recommandé)

Le webhook est le mécanisme le plus rapide et le plus économe en ressources. Dès que SasPay notifie PichFlow du succès d’une transaction, celle-ci est marquée comme réussie et le wallet du marchand est instantanément crédité.

---

## 2. Endpoint de Vérification Active (`verify`)

Pour les applications mobiles ou les pages d’attente client, vous pouvez interroger le statut en temps réel :
```
curl -X GET https://api.pichflow.com/v1/payments/pay_soft_abc12345/verify \
  -H "Authorization: Bearer sk_test_votre_cle"

```

### Réponse officielle :
```
{
  "success": true,
  "data": {
    "id": "pay_soft_abc12345",
    "reference": "TX-PF-883491",
    "status": "completed",
    "amount": "10000.00",
    "net_amount": "9800.00",
    "fee": "200.00",
    "currency": "XOF",
    "network": "mtn_bj",
    "paid_at": "2026-10-15T00:35:12Z"
  }

```

---

## Statuts Possibles

| **Statut SasPay**               | **Signification**                                                            | **Action Requise**                                          |
| :------------------------------ | :--------------------------------------------------------------------------- | :---------------------------------------------------------- |
| **`pending`**                   | Demande transmise à l’opérateur, en attente de validation USSD par le client | Continuer le polling (intervalle de 3 à 5 secondes)         |
| **`completed`** / **`success`** | Fonds prélevés et confirmés par l’opérateur                                  | Livrer le produit ou valider la commande immédiatement      |
| **`failed`**                    | Échec (solde client insuffisant, code PIN erroné, timeout)                   | Inviter le client à réessayer ou choisir un autre opérateur |
| **`cancelled`**                 | Paiement explicitement refusé par le client                                  | Clôturer la tentative                                       |

---

## Bonnes Pratiques de Polling

- **Intervalle minimal** : 3 000 ms (3 secondes). Évitez les requêtes à haute fréquence qui risquent d’entraîner une erreur HTTP **`429 Too Many Requests`**.
- **Délai maximum** : 180 secondes (3 minutes). Au-delà, affichez un message rassurant indiquant que le paiement est en cours de réconciliation sur le réseau opérateur.
- **Dédoublonnage & Idempotence** : Si un webhook arrive pendant que votre frontend effectue un polling, le mécanisme de règlement atomique PichFlow garantit qu’aucun compte n’est crédité deux fois.

# Gestion des Clients & Transactions

Recherche, filtrage, export CSV et téléchargement de factures PDF pour la comptabilité.

# Gestion des Clients & Transactions

PichFlow centralise l’ensemble de vos flux financiers et vos carnets clients avec un niveau de détail élevé.

---

## 1. Lister et Filtrer les Transactions

Interrogez l’historique complet de vos encaissements :
```
curl -X GET "https://api.pichflow.com/v1/transactions?limit=20&status=success" \
  -H "Authorization: Bearer sk_test_votre_cle"

```

### Paramètres de recherche supportés

- **`status`** : Filtrer par **`success`**, **`pending`**, **`failed`**, **`cancelled`**.
- **`limit`** : Nombre de résultats par page (par défaut: 20, max: 100).
- **`offset`** : Décalage pour la pagination.
- **`search`** : Recherche textuelle par référence, email ou nom de client.
- **`applicationId`** : Filtrer sur une application spécifique de votre compte.

---

## 2. Export Comptable CSV

Téléchargez l’ensemble de votre relevé de transactions pour l’intégrer dans vos outils comptables (Excel, QuickBooks, SAP) :
```
curl -X GET "https://api.pichflow.com/v1/transactions/export?format=csv" \
  -H "Authorization: Bearer sk_test_votre_cle" \
  --output relevé_transactions_pichflow.csv

```

Le fichier CSV exporté contient :

- Référence de la transaction
- Date et heure UTC
- Nom, email et téléphone du client
- Opérateur et pays (ex: **`MTN Bénin (BJ)`**)
- Montant brut, frais de passerelle et montant net encaissé
- Statut final

---

## 3. Génération de Reçus et Factures PDF

Chaque transaction réussie dispose d’une route permettant d’éditer une facture normalisée au format PDF :
```
curl -X GET "https://api.pichflow.com/v1/transactions/tx_1728945600000/invoice" \
  -H "Authorization: Bearer sk_test_votre_cle" \
  --output facture_tx_1728945600000.pdf

```

---

1. PichFlow vérifie si l’adresse email existe déjà pour votre compte et cette application.
2. Si le client existe : son **`total_spent`** et son **`payment_count`** sont incrémentés, et sa date **`last_transaction_at`** est actualisée.
3. Si le client est nouveau : une fiche complète est immédiatement créée dans votre carnet d’adresses. Opérations\

   # Gestion des Erreurs & Codes HTTP
   PichFlow et SasPay utilisent des codes de statut HTTP conventionnels pour indiquer la réussite ou l’échec des requêtes API.
   ---
   ## 1. Codes de Statut HTTP
   Les codes ci-dessous sont des références générales mentionnées dans les pages existantes ; la spécification OpenAPI ne définit pas les réponses de toutes les routes. Consultez la référence de chaque opération avant de dépendre d’un code précis.
   | **Code HTTP**                   | **Définition**           | **Contexte fréquent**                                                                      |
   | :------------------------------ | :----------------------- | :----------------------------------------------------------------------------------------- |
   | **`200 OK`**                    | Succès                   | Requête exécutée normalement.                                                              |
   | **`201 Created`**               | Ressource créée          | Le code de réponse exact dépend de l’opération.                                            |
   | **`400 Bad Request`**           | Requête invalide         | Paramètre manquant, montant négatif, format de numéro invalide.                            |
   | **`401 Unauthorized`**          | Non authentifié          | Clé API absente ou préfixe non reconnu.                                                    |
   | **`403 Forbidden`**             | Accès refusé             | Clé révoquée, scope insuffisant ou **IP non déclarée dans la whitelist SasPay** (payouts). |
   | **`404 Not Found`**             | Ressource introuvable    | Transaction, session ou lien de paiement inexistant.                                       |
   | **`409 Conflict`**              | Conflit / Doublon        | Réutilisation d’une clé d’idempotence avec un payload différent.                           |
   | **`410 Gone`**                  | Ressource expirée        | Session de paiement arrivée à échéance.                                                    |
   | **`422 Unprocessable Entity`**  | Erreur métier opérateur  | Numéro de téléphone non éligible à la réception de Mobile Money.                           |
   | **`429 Too Many Requests`**     | Limite de débit atteinte | Trop d’appels simultanés sur un court intervalle (ralentissez le polling).                 |
   | **`500 Internal Server Error`** | Erreur interne           | Erreur inattendue côté serveur ou indisponibilité temporaire.                              |

   ## 3. Règle d’Or de l’Idempotence (`Idempotency-Key`)
   L’idempotence garantit qu’une requête exécutée plusieurs fois avec la même clé produit exactement le même effet qu’un appel unique.

   **Webhooks & Sécurité**\
   **Réception sécurisée des événements de paiement, validation de signature HMAC SHA-256 et protection contre les attaques par rejeu.**\
   \
   **​**\
   **Webhooks & Sécurité**\
   **Les webhooks permettent à PichFlow et à SasPay de notifier votre infrastructure backend en temps réel dès qu’un paiement, retrait ou transfert change d’état.**\
   **​**\
   **1. En-têtes HTTP Reçus**\
   **Chaque requête webhook envoyée vers votre endpoint contient les en-têtes suivants :**\
   **En-tête	Description**\
   **X-Webhook-Signature	Signature hexadécimale HMAC SHA-256 calculée sur le corps brut de la requête.**\
   **X-Webhook-Timestamp	Horodatage Unix en secondes au moment de l’émission.**\
   **Content-Type	application/json**\
   **​**\
   **2. Algorithme de Vérification de Signature (HMAC SHA-256)**\
   **Pour vous assurer que la notification provient bien de PichFlow / SasPay et n’a pas été interceptée ou modifiée en cours de route :**\
   **Vérifiez l’âge de l’horodatage : Rejetez immédiatement toute requête dont le X-Webhook-Timestamp diffère de plus de 300 secondes (5 minutes) par rapport à l’heure courante de votre serveur afin de bloquer les attaques par rejeu.**\
   **Construisez la chaîne de signature : Concaténez l’horodatage et le corps brut (raw body) de la requête séparés par un point :**\
   **payload = \`${timestamp}.${rawBody}\`**\
   **Calculez le HMAC SHA-256 avec votre clé secrète webhook (whsec\_...).**\
   **Comparez en temps constant (crypto.timingSafeEqual) pour prévenir les attaques temporelles (timing attacks).**\
   **​**\
   **Exemple d’implémentation en Node.js / TypeScript :**\
   **import crypto from 'crypto';**\
   **import { Request, Response } from 'express';**\
   \
   **export function handleWebhook(req: Request, res: Response) {**\&#xA;**&#x20; const signature = req.headers['x-webhook-signature'] as string;**\&#xA;**&#x20; const timestamp = req.headers['x-webhook-timestamp'] as string;**\&#xA;**&#x20; const rawBody = (req as any).rawBody || JSON.stringify(req.body);**\&#xA;**&#x20; const secret = process.env.PICHFLOW_WEBHOOK_SECRET!;**\
   \&#xA;**&#x20; // 1. Contrôle d'expiration (tolérance 300s)**\&#xA;**&#x20; const now = Math.floor(Date.now() / 1000);**\&#xA;**&#x20; const eventTime = parseInt(timestamp, 10);**\&#xA;**&#x20; if (isNaN(eventTime) || Math.abs(now - eventTime) > 300) {**\&#xA;**&#x20;   return res.status(400).send('Horodatage expiré ou invalide.');**\&#xA;**&#x20; }**\
   \&#xA;**&#x20; // 2. Calcul du HMAC SHA-256**\&#xA;**&#x20; const expectedSignature = crypto**\&#xA;**&#x20;   .createHmac('sha256', secret)**\&#xA;**&#x20;   .update(\`${timestamp}.${rawBody}\`)**\&#xA;**&#x20;   .digest('hex');**\
   \&#xA;**&#x20; // 3. Comparaison sécurisée en temps constant**\&#xA;**&#x20; const sigBuffer = Buffer.from(signature.toLowerCase(), 'utf8');**\&#xA;**&#x20; const expBuffer = Buffer.from(expectedSignature.toLowerCase(), 'utf8');**\
   \&#xA;**&#x20; if (sigBuffer.length !== expBuffer.length || !crypto.timingSafeEqual(sigBuffer, expBuffer)) {**\&#xA;**&#x20;   return res.status(400).send('Signature webhook invalide.');**\&#xA;**&#x20; }**\
   \&#xA;**&#x20; // 4. Traitement idempotent de l'événement**\&#xA;**&#x20; const event = req.body;**\&#xA;**&#x20; if (event.event === 'transaction.success') {**\&#xA;**&#x20;   const tx = event.data;**\&#xA;**&#x20;   console.log(\`Paiement confirmé : ${tx.reference} pour un montant de ${tx.amount}\`);**\&#xA;**&#x20;   // Mettre à jour votre commande en base de données**\&#xA;**&#x20; }**\
   \&#xA;**&#x20; // Toujours renvoyer un code 200 OK**\&#xA;**&#x20; res.status(200).json({ received: true });**\
   **}**\
   **​**\
   **3. Événements Pris en Charge**\
   **Événement	Description**\
   **transaction.success	Le paiement client a été validé avec succès par l’opérateur.**\
   **transaction.failed	La tentative de paiement a échoué (solde insuffisant, code erroné, timeout).**\
   **transaction.cancelled	Le client a annulé la saisie ou la redirection.**\
   **settlement.success	Le virement de retrait (payout) est confirmé sur le compte bénéficiaire.**\
   **settlement.failed	Le virement de retrait a échoué et le solde a été réintégré.**\
   **webhook.test	Événement émis lors d’un test ping depuis le Dashboard développeur.**\

   # FAQ & Dépannage
   Questions fréquentes, diagnostic des incidents de paiement et checklist de mise en production.
   # FAQ & Dépannage
   Retrouvez ici les réponses aux questions techniques récurrentes et les étapes recommandées avant de lancer votre solution en production.
   ---
   ## Problèmes Courants & Solutions
   ### 1. “Pourquoi mon paiement reste-t-il au statut ‘pending’ ?”
   - Le paiement Mobile Money attend que l’utilisateur valide l’invite USSD sur son téléphone en saisissant son code PIN secret.
   - Si le client ne reçoit pas l’invite : vérifiez qu’il dispose de réseau télécom suffisant et que son solde Mobile Money couvre le montant ainsi que les éventuels frais de retrait opérateur.
   - Certains opérateurs (notamment Orange) exigent la génération manuelle d’un code d’autorisation par le client avant l’opération.
   ### 2. “Erreur 403 ip_not_whitelisted lors d’un appel Payout”
   - SasPay impose par mesure de sécurité que toute clé effectuant un virement sortant provienne d’une adresse IP whitelistée.
   - Connectez-vous à votre [**Tableau de bord SasPay**](https://saspay.me/) > Paramètres de sécurité > Liste blanche IP, et renseignez l’adresse IP publique de votre serveur de production.
   ### 3. “Pourquoi ma signature webhook échoue-t-elle systématiquement ?”
   - Assurez-vous d’utiliser le **raw body** (corps brut avant tout parsing **`JSON.parse`** ou **`express.json()`**). Tout reformatage d’espace ou d’ordre de clés invalide le HMAC.
   - Vérifiez que l’horloge de votre serveur est synchronisée via NTP (**`X-Webhook-Timestamp`** tolère un écart maximal de 300 secondes).
   - Assurez-vous d’utiliser le secret configuré dans votre Dashboard SasPay (**`SASPAY_WEBHOOK_SECRET`**).
   ---
   ## Checklist de Mise en Production (Live)
   Avant d’activer votre clé **`sk_live_...`** auprès de vos vrais clients :
   - **Clés d’API** : Remplacez votre clé **`sk_test_`** par votre clé **`sk_live_`** dans vos variables d’environnement de production.
