## 5. Reproduire le checkout en trois étapes

### Étape 1 — Identité du client

Afficher les informations dans l'ordre prévu par mes captures :

- Prénom.
- Nom.
- E-mail.
- Numéro de contact, uniquement si le marchand a activé l'option correspondante.

Pour un montant fixe, afficher le montant du lien. Pour un montant libre, demander le montant.

Quand le client valide cette étape, conserve les informations saisies et affiche l'étape suivante sans recharger inutilement toute la page.

### Étape 2 — Pays et moyen de paiement

Afficher une liste déroulante de pays avec :

- Les drapeaux.
- Les noms des pays.
- Une barre de recherche fonctionnelle.
- Une sélection accessible sur mobile et ordinateur.

La recherche doit réellement filtrer les pays, sans se limiter à changer le texte d'un champ.

La liste doit inclure les pays réellement couverts par les méthodes SoftPay utilisables dans mon compte. La documentation décrit notamment les méthodes suivantes :

- Bénin : MTN, Moov, Celtis Cash.
- Sénégal : Orange Money, Free Money, Expresso, Wave, Wizall, Djamo.
- Côte d'Ivoire : Orange Money, MTN, Moov, Wave, Djamo.
- Burkina Faso : Orange Money, Moov.
- Togo : T-Money, Moov.
- Mali : Orange Money, Moov.
- Cameroun : MTN.
- International : carte bancaire, sous réserve des conditions d'accès applicables.

Cette liste est une référence documentaire, pas la preuve que chaque méthode est activée dans mon compte sandbox. Vérifie chaque méthode, son endpoint, sa devise, ses paramètres et sa disponibilité réelle avant de la proposer comme opérationnelle.

Quand le client choisit un pays, affiche uniquement les moyens de paiement configurés pour ce pays. Par exemple, les options du Bénin ne doivent pas être remplacées par celles du Sénégal.

Si la liste officielle des pays ou des moyens disponibles n'est pas fournie automatiquement par l'API, utilise une configuration centrale vérifiée et documentée. Ne prétends pas qu'une liste est récupérée dynamiquement si ce n'est pas le cas.

Le champ de recherche doit fonctionner avec le nom du pays, et les sélections doivent être conservées lors du passage à l'étape suivante.

### Étape 3 — Numéro de paiement et confirmation

Après le choix du pays et de la méthode, demande le numéro utilisé pour effectuer le paiement lorsque cette méthode le nécessite.

Ce numéro est distinct du numéro de contact éventuellement demandé à l'étape 1.

Le bouton « Payer » doit lancer le véritable flux de paiement correspondant à la méthode sélectionnée.

Affiche un dialogue de confirmation avec un indicateur de progression. Donne au client des instructions adaptées : validation sur son téléphone, code de confirmation ou redirection sécurisée, selon le protocole officiel de la méthode.

Ne demande jamais de code PIN Mobile Money ou de mot de passe bancaire dans un formulaire PichFlow non prévu à cet effet.

## 6. Corriger la logique PayDunya pour chaque méthode

Ne crée pas un endpoint générique supposant que toutes les méthodes fonctionnent de la même façon.

Pour chaque moyen de paiement :

1. Vérifie l'endpoint exact dans la documentation officielle.
2. Vérifie le nom de chaque champ requis.
3. Vérifie les en-têtes et le jeton de facture attendu.
4. Vérifie le format du numéro de téléphone.
5. Vérifie les éventuels paramètres supplémentaires.
6. Vérifie si la réponse signifie « paiement terminé » ou seulement « paiement initié ».
7. Gère correctement les redirections et les confirmations complémentaires.
8. Enregistre la référence PayDunya et la référence interne PichFlow.
9. Vérifie le statut final côté serveur.

N'utilise pas le même corps JSON pour MTN Bénin, Wave Sénégal et les autres méthodes si leurs contrats API diffèrent.

La carte bancaire SoftPay doit être proposée uniquement si les conditions de certification et d'activation sont satisfaites. Sinon, indique clairement le blocage et utilise uniquement une solution sécurisée effectivement autorisée.

Si une méthode ne peut pas être testée dans mon sandbox, conserve son état comme non vérifié et indique la raison.

## 7. Frais : afficher les montants réels

Je souhaite que le client puisse supporter les frais applicables lorsque la méthode PayDunya le permet.

Examine la documentation de chaque méthode pour vérifier si les frais sont retournés dans la réponse et si le payeur les prend effectivement en charge.

Le checkout doit distinguer :

- Le montant du produit ou service.
- Les frais connus.
- Le total demandé au client.
- La devise.

N'invente aucun taux et n'ajoute pas une surcharge arbitraire. Ne déduis pas les frais deux fois.

Si le fournisseur ne retourne les frais qu'après une étape donnée, adapte le parcours en fonction de ce qui est techniquement possible. N'affiche pas de frais fictifs pour donner l'impression que la fonctionnalité est terminée.

## 8. Corriger les statuts de paiement

Le client doit voir un statut compréhensible :

- Paiement en cours.
- Paiement réussi.
- Paiement échoué.
- Paiement annulé.

Le simple succès de la requête d'initialisation ne signifie pas que le paiement est terminé.

Le backend doit vérifier le statut réel auprès de PayDunya ou traiter une notification serveur dont l'authenticité a été vérifiée. Une page de retour navigateur ne suffit pas.

Empêche les doubles soumissions et les doubles comptabilisations. Si le client revient sur la page, ne crée pas une nouvelle transaction payée automatiquement.

## 9. Vérifier l'isolation des applications

Chaque lien, checkout et transaction doit appartenir à l'application qui l'a créé.

Les données d'une application ne doivent jamais apparaître dans une autre. Le backend doit contrôler cette propriété dans les requêtes, et pas uniquement dans l'interface.

Teste au moins deux applications et vérifie que les liens, transactions, clients et statistiques restent indépendants.
