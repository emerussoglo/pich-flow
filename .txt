# MISSION CRITIQUE — AUDIT, RÉPARATION ET FINALISATION COMPLÈTE DU BACKEND PICHFLOW

Tu interviens sur le dépôt existant de PichFlow. Le frontend et la migration vers Next.js ont déjà été réalisés en grande partie, mais de nombreux problèmes subsistent dans le backend, la base de données, les paiements, le dashboard et la documentation.

Je ne veux plus de modifications superficielles. Je veux que tu inspectes le code réel, identifies les causes des erreurs, répares les fonctionnalités et prouves leur fonctionnement par des tests.

**Notre produit est PichFlow. Notre prestataire de paiement est PayDunya. SaaSPay est un concurrent et ne fait pas partie de notre produit.**

Ne recommence pas le projet de zéro. Préserve le travail valide déjà réalisé.

# PHASE 1 — SÉCURISER ET AUDITER LE PROJET

Avant de modifier quoi que ce soit :

1. Vérifie la branche Git et `git status`.
2. Préserve toutes les modifications existantes.
3. Inspecte `package.json`, la configuration Next.js, `src/app/`, `src/server/`, `src/lib/`, les modèles, les migrations, les tests et la documentation.
4. Identifie le moteur SQLite utilisé et le fichier ou service qui contient la base de données réelle.
5. Cartographie toutes les routes API et les fonctionnalités du dashboard.
6. Identifie les fonctionnalités réellement opérationnelles, celles qui sont incomplètes et celles qui sont simulées.
7. Vérifie la configuration de production et les variables d'environnement utilisées.

Ne lance aucune commande destructive. Ne supprime aucune donnée et ne réinitialise pas la base.

Travaille sur la branche de migration existante si elle est appropriée. N'écrase pas les changements non validés.

Fournis un bilan initial, puis commence les réparations concrètes.

# PHASE 2 — CORRIGER L'ERREUR SQLITE max_payments

Erreur observée lors de la création d'un lien de paiement :

`SQLITE_UNKNOWN: SQLite error: table payment_links has no column named max_payments`

Cette erreur doit être corrigée à la source.

Inspecte :

- le schéma réel de `payment_links` ;
- les requêtes d'insertion et de mise à jour ;
- les modèles TypeScript ;
- les migrations de base de données ;
- les fonctions de création des liens de paiement ;
- les tests associés.

Utilise notamment `PRAGMA table_info(payment_links)` sur une copie ou un environnement approprié pour vérifier les colonnes réelles.

Détermine si `max_payments` est une fonctionnalité voulue, une colonne oubliée dans une migration ou une référence obsolète.

Si la colonne est nécessaire, crée une migration additive et sûre compatible avec le moteur SQLite utilisé. Si elle n'est pas nécessaire, corrige proprement le code et les modèles concernés.

Ne supprime pas et ne recrée pas la table pour faire disparaître l'erreur.

La migration doit être reproductible, contrôlée et compatible avec une base déjà utilisée.

Vérifie que :
- les liens existants restent accessibles ;
- la création d'un nouveau lien fonctionne ;
- la modification d'un lien fonctionne si elle est implémentée ;
- la base conserve ses données ;
- le code et le schéma restent cohérents.

Recherche ensuite les autres colonnes référencées par le code mais absentes du schéma réel. Établis une liste des incohérences et corrige-les progressivement avec des migrations sûres.

N'ajoute pas aveuglément toutes les colonnes mentionnées dans le code : comprends d'abord le modèle métier.

# PHASE 3 — ÉLIMINER TOUTES LES RÉFÉRENCES À SAASPAY

SaaSPay est un concurrent. Il ne doit pas être utilisé comme fournisseur, comme identité de marque ni comme backend de PichFlow.

Recherche toutes ses références dans :
- les fichiers source ;
- les noms de fichiers et de dossiers ;
- les routes API ;
- les variables d'environnement ;
- les noms de variables et de fonctions ;
- les services de paiement ;
- les migrations et les schémas ;
- les exemples de code ;
- les tests ;
- la documentation ;
- les configurations de déploiement ;
- les textes visibles dans l'interface.

Pour chaque référence, identifie son rôle avant de la modifier.

Supprime les pages, composants, services et configurations propres à SaaSPay qui ne sont pas nécessaires au fonctionnement de PichFlow.

Remplace les références visibles par des informations exactes concernant PichFlow et PayDunya.

Ne réalise pas un remplacement global aveugle. Préserve les fonctionnalités génériques qui auraient été créées pendant la phase d'inspiration.

Ne supprime aucune variable PayDunya valide.

Ne supprime pas les références historiques nécessaires aux migrations sans vérifier leurs conséquences. Si une référence interne doit être conservée temporairement pour assurer la compatibilité, explique-la et isole-la du produit et de la documentation publique.

Après le nettoyage, effectue une nouvelle recherche globale. Le rapport doit distinguer les références actives supprimées des éventuelles occurrences historiques conservées.

# PHASE 4 — .ENV ET CONFIGURATION DES SECRETS

Le fichier `.env` actuellement utilisé est la source de configuration prioritaire pour l'environnement local.

Inspecte les variables réellement lues par le code. Vérifie les noms exacts, les valeurs attendues et les dépendances.

Ne remplace pas arbitrairement les variables existantes par des noms supposés.

- Conserve les variables PayDunya déjà correctement configurées.
- Retire les variables SaaSPay devenues inutiles après vérification des dépendances.
- Ne copie aucune clé secrète dans le code source.
- Ne publie jamais les secrets dans le frontend.
- Ne révèle pas les valeurs des secrets dans le terminal ou le rapport final.
- Ne remplace pas le `.env` existant par un fichier d'exemple.
- Conserve les variables nécessaires aux autres services réellement utilisés.

Si `.env.example` est utile, crée-le avec des placeholders uniquement. Il ne doit jamais remplacer `.env`.

Documente séparément les variables de test et de production. Le passage en mode live doit être explicite et ne doit jamais se produire automatiquement parce qu'une variable manque.

# PHASE 5 — INTÉGRATION PAYDUNYA RÉELLE

PayDunya est le seul prestataire de paiement externe visé par cette mission.

Documentation officielle :
https://developers.paydunya.com/doc/FR/http_json

Vérifie les endpoints et les paramètres directement dans la documentation officielle avant de modifier l'intégration.

Commence par auditer le service PayDunya existant, les clés configurées, les modes sandbox et live, les requêtes réseau et les modèles de transactions.

Utilise les clés sandbox existantes sans les afficher ni les demander dans la conversation.

## Création du paiement

Le flux doit fonctionner ainsi :

1. Le marchand crée un lien de paiement PichFlow.
2. Le lien est enregistré dans la base et rattaché à une application.
3. Le client ouvre le lien public.
4. Il remplit ses informations.
5. Le backend valide le lien, le montant, la devise et les informations du client.
6. PichFlow crée une transaction interne avec un identifiant unique.
7. Le backend appelle PayDunya en mode sandbox.
8. PichFlow enregistre les références et les informations nécessaires.
9. Le client accède au parcours de paiement PayDunya.
10. PichFlow vérifie le résultat selon les mécanismes officiels.
11. La transaction est mise à jour après confirmation vérifiée.
12. Le dashboard, le portefeuille, l'historique et la page client reflètent les données réelles.

Ne simule pas une réussite lorsque PayDunya n'est pas accessible.

Ne marque jamais une transaction comme payée uniquement parce que le navigateur revient sur une URL de succès.

Les appels PayDunya doivent être réalisés côté serveur. Les clés privées ne doivent jamais être envoyées au client.

## Webhooks et statuts

Vérifie les mécanismes de notification et de vérification de statut réellement pris en charge.

- Valide les notifications selon la documentation PayDunya.
- Vérifie les statuts et références.
- Empêche le double traitement d'une même notification.
- Assure l'idempotence des opérations financières.
- Conserve une trace des transitions de statut.
- N'accorde aucun crédit financier pour une transaction non confirmée.
- Ne fais pas confiance au seul statut envoyé par le navigateur.

Teste le parcours dans le sandbox. Si les clés ou le compte ne permettent pas de réaliser une étape, explique exactement ce qui manque.

# PHASE 6 — LIENS DE PAIEMENT

Répare intégralement la création et l'utilisation des liens de paiement.

Le formulaire du marchand doit permettre de définir :
- le nom du produit ou service ;
- la description ;
- un montant fixe ou libre ;
- le montant lorsque nécessaire ;
- la devise réellement autorisée ;
- l'application propriétaire ;
- les éventuelles limites de paiement prévues par le modèle existant.

Supprime l'option « répercuter les frais de transaction » et sa logique de supplément personnalisé.

Les frais PayDunya doivent être traités conformément à la configuration réelle du prestataire. Ne prétends pas que le client ou le marchand supporte un frais précis sans vérification.

Le lien créé doit être persistant, accessible publiquement par son URL prévue et utilisable de bout en bout.

Valide le montant et les paramètres côté serveur. Un client ne doit pas pouvoir modifier un montant fixe en éditant la requête.

# PHASE 7 — PARCOURS CLIENT DU LIEN PUBLIC

Je veux le parcours suivant.

## Première page : informations du client

Lorsqu'un client ouvre un lien de paiement :

- afficher le nom de l'application ou du marchand ;
- afficher le produit ou service et sa description ;
- afficher le montant fixe, ou un champ de montant libre ;
- demander le prénom ;
- demander le nom ;
- demander l'adresse e-mail ;
- demander le numéro de téléphone, obligatoire.

Sur cette première page, le client ne doit pas encore choisir le pays ou le moyen de paiement.

Après validation des informations, passer à l'étape suivante.

## Deuxième page : pays et moyen de paiement

Afficher les moyens de paiement disponibles dans le cadre de l'intégration PayDunya.

Le client choisit le moyen de paiement et le pays, dans un ordre cohérent avec les capacités réelles de PayDunya. Les choix doivent être validés côté serveur.

Si un moyen de paiement nécessite un pays ou un numéro de téléphone précis, applique les validations correspondantes.

La liste des pays et moyens de paiement doit correspondre aux pays et moyens effectivement disponibles pour le compte et le produit PayDunya utilisés.

Ne présente pas des options non prises en charge. N'invente pas une disponibilité géographique.

## Troisième étape : paiement

Lance le paiement réel via PayDunya sandbox.

Affiche un état de progression lorsque la transaction est en cours. Permets au client de comprendre qu'il doit terminer le parcours sécurisé du prestataire si une redirection ou une validation supplémentaire est requise.

N'enregistre pas les codes secrets Mobile Money dans PichFlow.

À la fin, affiche un résultat cohérent avec le statut vérifié : confirmé, en attente, échoué ou annulé, selon les états supportés.

Le paiement confirmé doit mettre à jour la bonne transaction, la bonne application et les vues du dashboard correspondantes.

# PHASE 8 — PORTFEUILLES ET SOLDES

Tous les portefeuilles ou moyens de paiement que nous sommes effectivement autorisés à utiliser doivent apparaître dans l'interface sans activation manuelle préalable.

Ne crée pas un faux solde pour rendre les wallets visuellement actifs.

Il faut distinguer :
- les moyens de paiement disponibles ;
- les soldes effectivement consultables auprès du prestataire ;
- les montants calculés à partir des transactions PichFlow ;
- les montants en attente ;
- les montants confirmés ;
- les montants réellement disponibles pour retrait, si cette fonctionnalité existe.

Un wallet doit être visible par défaut, mais son solde doit être fourni par une source réelle et vérifiée.

Ne crée pas une fausse correspondance entre une transaction PayDunya et un solde de wallet.

Si PayDunya ne fournit pas de solde indépendant pour un moyen de paiement ou un pays, affiche l'information disponible et explique la limitation. Ne présente pas le total des transactions comme un solde officiel du prestataire.

Les données doivent être rattachées à la bonne application. Aucun solde ne doit provenir d'une autre application.

# PHASE 9 — CLIENTS, TRANSACTIONS ET HISTORIQUE

La page Clients doit afficher les personnes ayant réellement effectué ou tenté de payer via les liens de paiement, selon les statuts et le modèle métier.

Conserve les informations pertinentes, selon les données réellement recueillies :
- prénom ;
- nom ;
- e-mail ;
- téléphone ;
- application propriétaire ;
- référence de transaction ;
- lien de paiement utilisé ;
- montant et devise ;
- date de création ;
- date et statut du paiement.

Évite de dupliquer inutilement les clients si le modèle prévoit une identité client réutilisable. Conserve toutefois l'historique de chaque transaction.

La page Historique doit afficher les événements et transactions associés à l'application sélectionnée.

Vérifie les relations de base de données et ajoute les migrations nécessaires de manière additive et sûre.

N'enregistre que les données nécessaires. N'enregistre jamais de code secret Mobile Money ou de données de carte bancaire sensibles dans PichFlow.

# PHASE 10 — ISOLATION STRICTE DES APPLICATIONS

Un compte peut avoir plusieurs applications. Chacune possède son propre périmètre de données.

Toutes les requêtes de lecture et d'écriture doivent vérifier les autorisations côté serveur.

Pour chaque application, isole :
- les liens de paiement ;
- les clients et leurs transactions ;
- les historiques ;
- les statistiques ;
- les soldes et portefeuilles ;
- les rapports ;
- les clés API et intégrations propres à l'application, si le modèle le prévoit.

Le frontend ne doit jamais pouvoir forcer l'accès à une application en envoyant simplement un identifiant différent.

Lors d'un changement d'application, recharge les données pertinentes et évite d'afficher momentanément le solde précédent comme s'il appartenait à la nouvelle application.

Ajoute des tests avec deux applications distinctes et des données différentes.

# PHASE 11 — AUTHENTIFICATION ET NAVIGATION DU DASHBOARD

L'authentification doit rester sécurisée, mais la vérification de session ne doit pas créer inutilement une nouvelle opération coûteuse à chaque navigation.

Audite le mécanisme actuel avant de le modifier.

- Identifie les requêtes de vérification de session déclenchées à chaque changement de page.
- Réutilise un état d'authentification partagé lorsque c'est compatible avec l'architecture existante.
- Évite les vérifications identiques déclenchées en double.
- Préserve la vérification côté serveur pour les opérations sensibles.
- Ne conserve pas un état d'authentification périmé indéfiniment.
- Gère correctement l'expiration de session et la déconnexion.
- Empêche les appels aux endpoints privés avant que l'état d'authentification soit correctement déterminé.

N'enlève pas les contrôles d'autorisation pour améliorer la vitesse.

Mesure ou compare le nombre de requêtes avant et après les changements.

# PHASE 12 — API PUBLIQUE PICHFLOW

PichFlow doit permettre aux marchands d'intégrer les paiements à leurs propres sites.

L'API publique doit appeler le backend PichFlow, qui appelle PayDunya côté serveur.

Utilise une API versionnée, par exemple :

`https://pichflow.vercel.app/api/v1/`

Respecte le domaine réel configuré dans le projet.

Examine les routes existantes avant de créer de nouvelles routes. Ne duplique pas les fonctionnalités.

Prévois, selon le périmètre effectivement implémenté :
- la gestion des clés API PichFlow ;
- la création de liens de paiement ;
- la création de sessions de paiement ;
- la consultation du statut d'une transaction ;
- les notifications ou webhooks nécessaires ;
- les erreurs et codes HTTP ;
- la validation des données ;
- l'isolation des applications ;
- la révocation et la rotation des clés ;
- des mécanismes d'idempotence adaptés aux opérations financières.

Les clés API PichFlow doivent être distinctes des clés privées PayDunya.

Ne publie jamais une clé secrète dans le frontend.
