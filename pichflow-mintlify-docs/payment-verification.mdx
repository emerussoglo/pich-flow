# Vérifier un paiement

Le serveur offre deux lectures distinctes. Elles ne prennent pas le même identifiant.

## Statut fournisseur par identifiant

```bash
curl http://localhost:3000/api/v1/payments/pay_demo_001/verify \
  -H "Authorization: Bearer $PICHFLOW_API_KEY"
```

Le chemin `:id` est transmis à SasPay et la réponse enveloppe le résultat dans `data` lorsque l'appel est réussi.

## Statut interne par référence

```bash
curl http://localhost:3000/api/v1/payments/status/TX-DEMO-001 \
  -H "Authorization: Bearer $PICHFLOW_API_KEY"
```

Cette route recherche `reference` dans la base de PichFlow et renvoie l'objet `transaction` ou HTTP 404 si la référence n'est pas trouvée.

## Statuts et confirmation

Les valeurs de statut proviennent du fournisseur ou de la base interne; le code ne garantit pas un ensemble stable commun à toutes les réponses. Traitez les états inconnus comme non confirmés et ne livrez pas une commande sur la seule base d'une redirection navigateur.

L'API PichFlow possède aussi un récepteur entrant SasPay et met à jour certaines lignes lorsque des événements de succès ou d'échec arrivent. La livraison de notifications sortantes à vos propres endpoints n'est pas opérationnelle dans le dispatcher actuellement présent dans ce dépôt; voir [Webhooks](./webhooks).
