# Retraits et payouts

## Initialiser un payout

`POST /api/v1/payouts/initialize` exige une clé dont le scope est `payout` ou `both`. Le corps attendu par le handler contient `amount`, `currency`, `country`, `method` et `recipient.msisdn`.

```bash
curl -X POST http://localhost:3000/api/v1/payouts/initialize \
  -H "Authorization: Bearer $PICHFLOW_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: d4e5f6a7-8901-4b2c-aef0-123456789abc" \
  -d '{
    "amount": "50000.00",
    "currency": "XOF",
    "country": "BJ",
    "method": "mtn_bj",
    "recipient": {
      "msisdn": "+22997000000"
    },
    "description": "Payout de démonstration"
  }'
```

`customer`, `description` et `fee_charge_mode` peuvent aussi être transmis. Le handler vérifie d'abord le solde local et renvoie `422` avec `insufficient_balance` lorsque le solde est insuffisant. L'en-tête `Idempotency-Key` est facultatif dans le code; une valeur est générée si elle manque.

La réponse de succès inclut `success`, `environment` et `data` renvoyé par le fournisseur. Aucun schéma de payout complet n'est construit dans le handler.

## Vérifier le payout

```bash
curl http://localhost:3000/api/v1/payouts/payout_demo_001/verify \
  -H "Authorization: Bearer $PICHFLOW_API_KEY"
```

Le résultat est transmis par SasPay sous `data` si réussi, sinon sous `error` et éventuellement `data`.

Le code traduit certaines erreurs fournisseur `403` en `ip_not_whitelisted`. Cela ne permet pas de conclure que tous les comptes nécessitent une IP déclarée; vérifiez le message concret de votre environnement. Les retraits du tableau de bord à `/api/withdrawals` sont une autre fonctionnalité, authentifiée par session.
