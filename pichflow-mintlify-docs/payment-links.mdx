# Liens de paiement

Les liens de paiement sont gérés par des routes du tableau de bord protégées par la session utilisateur. Le code ne déclare pas de route `/api/v1/payment-links` authentifiée par clé API.

## Routes confirmées dans le serveur

| Méthode | Route | Accès |
|---|---|---|
| `GET` | `/api/payment-links` | Session du compte; accepte `applicationId` ou `appId` en query. |
| `POST` | `/api/payment-links` | Session du compte; `title` est requis. |
| `GET` | `/api/payment-links/slug/:slug` | Lecture publique d'un lien actif. |
| `GET` | `/api/payment-links/:id` | Session du compte. |
| `PUT` | `/api/payment-links/:id` | Session du compte. |
| `DELETE` | `/api/payment-links/:id` | Session du compte. |

Le middleware de session accepte un jeton Bearer de session; ces routes ne doivent pas être appelées avec une clé `sk_test_` ou `sk_live_`.

## Création (tableau de bord)

Le handler reconnaît `title` (requis), `description`, `amount`, `isFixedAmount`, `currency`, `country`, `usageLimit`, `requirePhone`, `expiresAt`, `redirectUrl` et `applicationId`. Il renvoie `success` et `paymentLink`, y compris `paymentUrl`. Le slug est construit par le serveur; l'application sélectionnée doit appartenir à l'utilisateur.

```json
{
  "title": "Commande de démonstration",
  "description": "Lien de test",
  "amount": 2500,
  "isFixedAmount": true,
  "currency": "XOF",
  "country": "BJ",
  "requirePhone": false,
  "expiresAt": "2027-10-19"
}
```

Un lien à montant libre doit omettre `amount`; le serveur le rejette s'il en reçoit un. Les montants fixes sont des entiers XOF d'au moins 200. `country` peut être omis; la configuration vérifiée de ce dépôt ne prend en charge que le Bénin (BJ) en XOF. Les codes PayDunya documentés pour les autres pays sont conservés dans le catalogue commun, mais ne sont pas présentés comme actifs tant que leur activation sur le compte n'est pas vérifiée. MTN Cameroun correspond à XAF (distinct de XOF), qui n'est pas activé dans le flux courant. `expiresAt` est une date `YYYY-MM-DD` et expire à la fin de cette journée UTC.

Le checkout public ne demande le numéro de contact que si `requirePhone` est vrai. Le montant libre est saisi à la première étape; le montant fixe y est affiché sans possibilité de modification. La recherche de pays filtre le catalogue central et la liste native est accessible au clavier et sur mobile.

Le serveur utilise la facture hébergée (`/checkout-invoice/create`) puis la vérification (`/checkout-invoice/confirm/{invoice_token}`). Il n'appelle pas les endpoints SoftPay spécifiques aux opérateurs. Ceux-ci ont des champs propres à chaque réseau; le guide Sandbox ne décrit qu'un endpoint générique nécessitant les identifiants du compte client de test, mot de passe inclus. Ce mot de passe n'est pas collecté par PichFlow. L'API SoftPay carte exige PCI-DSS et activation. Les méthodes documentées ne sont donc pas présentées comme des options directes fonctionnelles; le client choisit parmi les méthodes activées sur la page sécurisée.

Le catalogue documentaire ne constitue pas une liste d'activation du compte, et PayDunya ne documente pas d'API de capacités utilisée par PichFlow. Le checkout ne propose pour l'instant que Bénin (BJ) / XOF; une facture sandbox créée ne prouve ni l'activation d'un opérateur, ni un paiement complété. Certaines réponses SoftPay peuvent fournir `fees` et `currency`, mais le checkout hébergé utilisé ici ne fournit pas de frais vérifiés avant redirection : PichFlow n'ajoute donc aucune surcharge.

En production, configurez `APP_URL` avec l'origine HTTPS publique. En local, configurez `PAYDUNYA_CALLBACK_URL` avec l'URL HTTPS d'un tunnel vers `/api/webhooks/paydunya` pour recevoir les IPN; le callback vers localhost n'est pas joignable depuis PayDunya.
