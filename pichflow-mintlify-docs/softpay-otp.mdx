# Softpay et confirmation OTP

## Initialiser un paiement

```bash
curl -X POST http://localhost:3000/api/v1/payments/softpay \
  -H "Authorization: Bearer $PICHFLOW_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: e3c45678-1234-4a5b-bcde-9876543210ab" \
  -d '{
    "amount": "10000.00",
    "currency": "XOF",
    "country": "BJ",
    "network": "mtn_bj",
    "customer": {
      "first_name": "Koffi",
      "last_name": "Exemple",
      "email": "koffi@example.test",
      "phone": "+22997000000"
    },
    "description": "Paiement de démonstration",
    "fee_charge_mode": "ADD_ON"
  }'
```

Le handler exige `amount`, `network` et `customer`. `currency` vaut `XOF` et `country` `BJ` par défaut. `description`, `fee_charge_mode` et `otp` sont également transmis au fournisseur. `Idempotency-Key` est facultatif côté serveur; si omis, une nouvelle valeur est créée à chaque requête.

## Confirmer un OTP

Si le flux fournisseur requiert un OTP, transmettez-le à la route de confirmation avec l'identifiant de paiement renvoyé par le fournisseur :

```bash
curl -X POST http://localhost:3000/api/v1/payments/pay_demo_001/confirm-otp \
  -H "Authorization: Bearer $PICHFLOW_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"otp":"123456"}'
```

Le handler exige une valeur `otp` et transmet son texte au fournisseur. Les réseaux qui exigent un OTP, le mode de génération du code et les formats de réponse ne sont pas déterminés par le code PichFlow.

## Retry

`POST /api/v1/payments/:id/retry` transmet l'identifiant au fournisseur. Le handler accepte `Idempotency-Key` et en génère une si elle manque. Vérifiez d'abord le statut et réutilisez une clé stable seulement pour une même intention de retry.
