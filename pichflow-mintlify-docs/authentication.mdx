# Authentification et clés API

Les routes `/api/v1/...` de l'API marchande passent par le middleware `requireApiKey`. Celui-ci attend un en-tête HTTP Bearer :

```http
Authorization: Bearer <votre_clé_api>
```

Ne placez pas une clé secrète dans du code livré au navigateur, une application mobile non sécurisée, un dépôt Git ou une variable publique.

## Environnements

La route de création de clés du tableau de bord génère deux secrets :

| Environnement | Préfixe | Utilisation |
|---|---|---|
| Sandbox | `sk_test_` | Requêtes traitées dans l'environnement sandbox associé à la clé. |
| Live | `sk_live_` | Requêtes traitées dans l'environnement live associé à la clé. |

Le middleware associe l'environnement à la clé, et les réponses de plusieurs routes le renvoient dans `environment`. Les garanties de simulation, les fonds impliqués et les règles d'activation ne sont pas spécifiés par le serveur; confirmez-les avant un appel Live.

## Générer et révoquer

Dans le tableau de bord, la route `POST /api/developer/keys` crée une paire et renvoie les clés complètes dans sa réponse de création. La route `DELETE /api/developer/keys/:id` révoque une clé. Ces deux routes utilisent la session du compte et ne font pas partie de la référence publique par clé API.

## En-têtes facultatifs

Pour les opérations financières, fournissez une valeur unique et persistante dans `Idempotency-Key`. Le code génère une valeur si elle est omise sur les routes Softpay, retry, payout et transfert; cela évite cependant à votre client de contrôler l'identité du retry. La clé n'est pas exigée par le middleware d'authentification.

## Exemple

```bash
curl http://localhost:3000/api/v1/transactions \
  -H "Authorization: Bearer $PICHFLOW_API_KEY"
```
