# API PichFlow v1

Cette page décrit uniquement les opérations versionnées implémentées dans le dépôt. PichFlow crée et vérifie les factures PayDunya côté serveur; les intégrateurs ne reçoivent jamais de secret PayDunya.

## Origines et environnements

| Environnement | URL de base |
| --- | --- |
| Production actuelle | `https://pichflow.vercel.app/api/v1` |
| Développement local | `http://localhost:3000/api/v1` |

Le même chemin `/api/v1` peut être servi ultérieurement derrière un domaine API personnalisé; aucune configuration DNS de ce futur domaine n'est requise actuellement.

Le backend accepte XOF et utilise actuellement le pays BJ (Bénin) pour ces liens. La prise en charge effective du compte PayDunya doit être confirmée avant de présenter ce parcours comme disponible en production. Les autres devises, pays, paiements directs, payouts et transferts ne sont pas exposés par cette API v1.

## Authentification des intégrateurs

Créez une clé depuis le centre développeur de l'application PichFlow. Les secrets sont préfixés `pf_test_` ou `pf_live_`, rattachés à une application et stockés sous forme de hash. La valeur complète est montrée à la création; conservez-la côté serveur. Révoquez une clé compromise depuis le centre développeur.

```http
Authorization: Bearer pf_test_<secret>
Content-Type: application/json
```

Les clés ne doivent jamais être envoyées au navigateur. L'application propriétaire de la clé est déterminée par la base de données, et non par un `applicationId` fourni dans la requête. Un lien ou paiement d'une autre application renvoie une erreur introuvable.

Chaque requête de création génère une seule clé. Demandez les clés Sandbox et Live séparément; une clé Live exige que `PAYDUNYA_MODE=live` soit explicitement configuré. Révoquez puis recréez une clé compromise.

Le mode `PAYDUNYA_MODE` côté serveur doit correspondre à l'environnement de la clé. En développement, l'absence de cette variable choisit le sandbox; en production, la configuration doit être explicite et aucun basculement automatique vers le mode live n'est effectué.

## Liens de paiement

### Lister les liens

`GET /payment-links` liste les liens de l'application associée à la clé.

```bash
curl "https://pichflow.vercel.app/api/v1/payment-links" \
  -H "Authorization: Bearer pf_test_<secret>"
```

La réponse contient `success: true` et `data`, une liste d'objets avec `id`, `slug`, `name`, `description`, `amount`, `isFixedAmount`, `currency`, `country`, `status`, `usageCount`, `usageLimit` et `createdAt`.

### Créer un lien

`POST /payment-links` accepte `type: "fixed"` ou `type: "free"`. Un montant fixe est un entier positif en XOF; pour un lien libre, omettez `amount`. `usageLimit` est facultatif et doit être un entier positif.

```bash
curl -X POST "https://pichflow.vercel.app/api/v1/payment-links" \
  -H "Authorization: Bearer pf_test_<secret>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Commande boutique",
    "description": "Commande 123",
    "type": "fixed",
    "amount": 5000,
    "currency": "XOF"
  }'
```

Le serveur fixe le pays à BJ et refuse toute devise autre que XOF. Un montant fourni par le client au checkout ne remplace jamais le prix fixe stocké dans le lien.

## Créer une session de paiement

`POST /checkout-sessions` nécessite une clé API `payin` et un en-tête `Idempotency-Key` stable pour les retries de la même intention. Fournissez exactement un `paymentLinkId` ou un `paymentLinkSlug`. Le prénom/nom peuvent être transmis dans `customerName`; l'e-mail et un téléphone béninois `+229` suivi de 8 chiffres sont obligatoires.

```bash
curl -X POST "https://pichflow.vercel.app/api/v1/checkout-sessions" \
  -H "Authorization: Bearer pf_test_<secret>" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-123-checkout-1" \
  -d '{
    "paymentLinkSlug": "commande-boutique-abc123",
    "customerName": "Awa Exemple",
    "customerEmail": "awa@example.test",
    "customerPhone": "+22997000000"
  }'
```

Pour un lien à montant libre, transmettez aussi `amount` comme entier XOF positif. Pour un montant fixe, le backend ignore la valeur fournie par le client et prend celle du lien. Une création réussie répond HTTP 201 et renvoie notamment `data.reference`, `data.status`, `data.amount`, `data.currency` et `data.checkoutUrl`. Redirigez le client vers `checkoutUrl`, hébergée par PayDunya.

Exemple JavaScript/TypeScript côté serveur :

```ts
const response = await fetch(
  "https://pichflow.vercel.app/api/v1/checkout-sessions",
  {
    method: "POST",
    headers: {
      Authorization: `Bearer ${process.env.PICHFLOW_API_KEY}`,
      "Content-Type": "application/json",
      "Idempotency-Key": `order-${order.id}-checkout-1`,
    },
    body: JSON.stringify({
      paymentLinkId: order.paymentLinkId,
      customerName: `${customer.firstName} ${customer.lastName}`,
      customerEmail: customer.email,
      customerPhone: customer.phone,
    }),
  },
);

const result = await response.json(); 
if (!response.ok) throw new Error(result.error);
return result.data.checkoutUrl;
```

Ne demandez pas le code secret Mobile Money dans votre site : le client poursuit le paiement dans le parcours sécurisé du prestataire.

## Vérifier le statut

`GET /payments/{reference}` re-vérifie auprès de PayDunya les sessions encore en attente. Les valeurs possibles sont `pending`, `success`, `failed` et `cancelled`. Un retour du navigateur n'est pas une preuve de paiement. Seul `success` confirme que le serveur a vérifié la facture.

```bash
curl "https://pichflow.vercel.app/api/v1/payments/pf_<uuid>" \
  -H "Authorization: Bearer pf_test_<secret>"
```

La réponse contient `data.reference`, `data.status`, `data.amount` et `data.currency`. Le paiement confirmé est crédité au solde en attente de l'application; il n'est pas présenté comme immédiatement retirable ou disponible chez PayDunya.

## Webhooks

PayDunya notifie `POST /api/webhooks/paydunya`, hors du préfixe v1. Le handler vérifie le hash SHA-512 attendu, puis re-confirme la facture auprès de PayDunya avant de régler la transaction. Une notification répétée ne crédite pas deux fois le portefeuille.

Les notifications marchandes configurées dans le tableau de bord reçoivent l'événement `payment.succeeded` après confirmation. Le corps comporte `id`, `event`, `created_at` et `data`; les en-têtes incluent `X-PichFlow-Event` et `X-PichFlow-Signature` (HMAC-SHA-256 du corps avec le secret du webhook). La livraison actuelle effectue une tentative et journalise son résultat; aucun mécanisme automatique de retry n'est implémenté. Votre endpoint doit être public et utiliser HTTPS.

## Erreurs HTTP

Les erreurs renvoient JSON sous la forme `{ "success": false, "error": "..." }`.

| Code | Signification courante |
| --- | --- |
| 400 | JSON, champs, devise ou clé d'idempotence invalides |
| 401 | Clé API manquante, invalide ou révoquée |
| 403 | Environnement ou portée de clé incompatible |
| 404 | Lien/paiement absent ou appartenant à une autre application |
| 409 | Réutilisation de la clé d'idempotence avec une autre intention |
| 410 | Lien inactif ou limite d'utilisation atteinte |
| 500 | Erreur serveur inattendue |
| 502/503 | Réponse ou configuration fournisseur indisponible |

Les erreurs de validation peuvent renvoyer un code 400; la liste ci-dessus n'exclut pas d'autres codes liés aux erreurs fournisseur.

## Configuration et limites

Les secrets PayDunya sont exclusivement serveur : `PAYDUNYA_MODE`, `PAYDUNYA_MASTER_KEY`, `PAYDUNYA_PRIVATE_KEY` et `PAYDUNYA_TOKEN`. N'exposez aucune de ces variables dans un préfixe public, une réponse HTTP ou un journal.

Les tests automatisés utilisent un fournisseur réseau simulé localement; ils ne constituent pas un paiement sandbox réel. Avant le live, configurez les clés appropriées dans Vercel, vérifiez les capacités du compte PayDunya et exécutez les validations sandbox et de déploiement. Aucun endpoint public documenté ici ne permet les payouts, transferts, Softpay direct, la création de webhooks par API ou l'accès cross-application.
