# Vue d'ensemble des paiements

Le serveur fournit trois voies d'initialisation côté API marchande :

| Opération | Route locale | Usage |
|---|---|---|
| Softpay | `POST /api/v1/payments/softpay` | Passe `amount`, `network` et l'objet `customer` au fournisseur. |
| Checkout hébergé | `POST /api/v1/checkout-sessions` | Crée une session et transmet au fournisseur les informations du client. |
| Création unifiée | `POST /api/v1/payments/create` | Choisit Softpay si `network` et `customerPhone` sont présents; sinon checkout hébergé. |

Toutes ces routes exigent `Authorization: Bearer <clé_API>`. La base locale est `http://localhost:3000`; l'hôte public et son préfixe n'ont pas été confirmés dans la configuration du dépôt.

## Quel flux choisir ?

- Utilisez **Softpay** si votre serveur dispose déjà du réseau, du téléphone et des informations client nécessaires.
- Utilisez **Checkout hébergé** si vous souhaitez recevoir une URL `checkout_url` à présenter au client.
- Utilisez **payments/create** si vous souhaitez déléguer le choix au serveur selon la présence de `network` et `customerPhone`.

Les réponses de ces appels encapsulent généralement le résultat fournisseur sous `data`; le schéma exact de cette donnée dépend de SasPay. Ne traitez pas une session créée comme une preuve de paiement réussi. Vérifiez le paiement ou attendez un événement confirmé.

Voir [Softpay et OTP](./softpay-otp), [Checkout hébergé](./hosted-checkout) et [Vérification](./payment-verification).
