# Erreurs et réponses HTTP

Les opérations renvoient JSON pour leurs erreurs contrôlées. Plusieurs handlers relaient le statut et le message du fournisseur; les codes possibles peuvent donc varier selon la route et l'environnement.

| Code | Cas confirmé dans le code |
|---|---|
| `400` | Corps requis manquant, montant invalide ou OTP absent sur les opérations concernées. |
| `401` | Clé API absente/invalide; signature de webhook SasPay invalide. |
| `403` | Scope de clé insuffisant pour le payout; certaines erreurs fournisseur `403` sont mappées à `ip_not_whitelisted`. |
| `404` | Référence de paiement ou transaction interne introuvable. |
| `422` | Solde insuffisant pour le payout via API marchande. |
| `500` | Erreur interne attrapée ou erreur des routes de référence. |

Les erreurs JSON utilisent généralement `success: false` et `error`; certaines incluent aussi `code`, `data` ou `environment`. Le code ne définit pas une enveloppe d'erreur uniforme pour toutes les routes.

## Exemple de gestion côté client

```ts
const response = await fetch(url, options);
const contentType = response.headers.get("content-type") ?? "";
const body = await response.text();

if (!contentType.includes("application/json")) {
  throw new Error(`Réponse non JSON (HTTP ${response.status})`);
}

const result = JSON.parse(body);
if (!response.ok || result.success === false) {
  throw new Error(result.error ?? `Échec HTTP ${response.status}`);
}
```

Ne traitez pas un timeout comme une preuve d'échec financier. Pour la même opération, réutilisez la même `Idempotency-Key` fournie par votre serveur puis vérifiez le statut avant toute nouvelle tentative.
